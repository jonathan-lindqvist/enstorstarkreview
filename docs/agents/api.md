# Native client API

Rules for the `/api/v1` backend used by the native app. Design decisions live in [docs/api.md](../api.md). Part of the agent guidance in [AGENTS.md](../../AGENTS.md).

## Native client API

`/api/v1` serves the native apps: the SwiftUI iOS app in `mobile/ios/` and the Kotlin Android app in `mobile/android/`. The web app is the primary client. The native apps are best effort: do not update, build, or fix them for web changes, and a broken native app never blocks work (they need Xcode or Android tooling that most contributors do not have). The `/api/v1` server code is part of the web backend and must stay correct.

## One procedure per feature

Every server feature is one oRPC procedure in `src/lib/server/rpc/procedures/`, listed in `rpc/router.ts` ([README](../../src/lib/server/rpc/README.md)). The API serves it from the catch-all `src/routes/api/[...path]/+server.ts` through `rpc/http.ts`; web loads and actions call the same procedure with `webClient(event)` from `rpc/web.ts` and map errors with `webFailure`/`webError`. Do not add `+server.ts` files under `src/routes/api/`, and do not put authentication, admission, version checks or error mapping in a web route when the procedure owns them.

- **Contract.** `openapi/v1.yaml` and `src/lib/types/api-v1.d.ts` are generated from the router: run `npm run api:generate`, never edit them. Run `npm run api:diff` to see what changed for clients compared with `origin/main`, and `npm run api:lint`. `rpc/openapi.test.ts` fails when either file is stale. Component names are used by the generated Swift and Kotlin clients: renaming an exported schema in `rpc/schemas.ts` is a breaking change. Breaking API changes are permitted; record them in `docs/api.md`.
- **Fields.** When you add, rename, or remove a review field, update `rpc/schemas.ts`, the mappers (`rpc/representations.ts` for responses, `rpc/review-input.ts` for requests, `rpc/metadata.ts` for form options), and the procedure tests in the same change. An unmapped field is silently reset by API edits.
- **Authentication.** Hooks authenticate `/api/*` only with bearer tokens (never the cookie) and web routes only with the cookie. Procedures read the result from their context. `.meta({ auth })` documents the security; `authenticated()` enforces it before any input is read and audits denied writes with a per-channel reason.
- **Input order.** Middleware declared before `.input()` runs before the body is read: authentication, anonymous IP admission (`admitLoginIp`, `admitReviewRequestIp`, passed into the workflow so the attempt is charged once; never accept admission from request input), `versionRequired()`. `apiInput()` then reads at most the schema's `x-max-body-bytes` of streamed bytes (413 with `Connection: close`), requires JSON (415), parses (400) and validates with Zod (422 at the first issue, Swedish detail, JSON pointer). Budgets: 16 KiB sessions/review requests, 22 MiB review writes. Base64 validation must use constant stack space and preserve the 15 MiB decoded limit.
- **Errors.** Throw `problem(code, swedishDetail, data?)` from `rpc/errors.ts` and declare the codes with `.errors(problems(…))`. The API door renders `application/problem+json` with `no-store`; unexpected errors become a generic 500 without details. `data.form` carries what a no-JavaScript web form needs to redisplay itself.
- **Versions.** Review PUT and DELETE require the version the caller saw: `If-Match` with a current strong tag on the API, the `version` query that the edit page puts on its edit and delete forms on the web. Missing is 428, stale/weak-only/wildcard 412, and a parallel write that wins the atomic `updatedAt` check 409. Reads marked `.meta({ cache: 'revalidate' })` get an ETag, `Vary: Authorization` and weak/wildcard `If-None-Match` 304s from the API door.
- **Tests.** Test a procedure with `call(router.x.y, input, { context: testContext({ deps }) })` and the fakes in `rpc/test-fixtures.ts`; cover anonymous, invalid, oversized, quota and dependency-failure paths and assert that no side effect happened. HTTP-only behavior (problem rendering, 304, unread bodies) belongs in `rpc/http.test.ts`, and web mapping in thin route tests.

See [docs/api.md](../api.md) for design decisions and compatibility.
