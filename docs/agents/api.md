# Native client API

Rules for the `/api/v1` backend used by the native app. Design decisions live in [docs/api.md](../api.md). Part of the agent guidance in [AGENTS.md](../../AGENTS.md).

## Native client API

`/api/v1` serves the native apps: the SwiftUI iOS app in `mobile/ios/` and the Kotlin Android app in `mobile/android/`. The web app is the primary client. The native apps are best effort: do not update, build, or fix them for web changes, and a broken native app never blocks work (they need Xcode or Android tooling that most contributors do not have). The `/api/v1` server code is part of the web backend and must stay correct.

**The `HttpApi` is the contract.** Endpoints are declared in `server/api/contract/api.ts` with their schemas in `server/api/contract/schemas.ts`, implemented in `server/api/handlers.ts`, and served by `src/routes/api/[...path]/+server.ts` through `HttpRouter`'s web handler. There are no per-endpoint route files. `openapi/v1.yaml` and `src/lib/types/api-v1.d.ts` are generated: change the `HttpApi`, then run `npm run api:generate` and `npm run api:lint`, and review the YAML diff (the iOS app symlinks it, Android generates from it, Playwright validates responses against it). `openapi.test.ts` fails when the YAML is stale; `contract.test.ts` checks operations and type freshness. Keep component names stable; `openapi.ts` post-processes the generator output for compatibility (see [docs/api.md](../api.md#effect-migration-and-the-generated-contract)).

When you add, rename, or remove a review field, or change a workflow or rule that the API exposes, update the schemas, the API mappers (`server/api/reviews.ts` for responses, `server/api/review-input.ts` for requests, `server/api/metadata.ts` for form options), and the API tests in the same change. An unmapped field is silently reset by API edits. Breaking API changes are permitted; record them in `docs/api.md`.

**Handlers reuse the workflows.** A handler authenticates or admits the request, reads and decodes the body, runs the same Effect workflow as the web action, and renders the result. Workflow errors are `Schema.TaggedError`s with an `httpApiStatus`; `server/api/problem.ts` renders them as `application/problem+json` with a stable `code`. Add the tag to its code map when you add an error.

API routes authenticate only with bearer tokens (the `Authentication` and `OptionalAuthentication` middlewares; never the cookie), accept only JSON, and return problem responses. Review PUT and DELETE require an explicit current strong `If-Match` tag: missing is 428, stale/weak-only/wildcard is 412; GET `If-None-Match` retains weak/wildcard matching. Web and API persistence use atomic `updatedAt` checks and return 409 if a parallel write wins. Request body budgets live in the request schemas' `x-max-body-bytes` annotation: 16 KiB sessions/review requests, 22 MiB authenticated review writes; count actual streamed bytes and return 413 before JSON parsing. Structural schema validation stops at the first error. Anonymous API routes consume the shared IP quota before parsing; pass server-owned IP admission into workflows to avoid double charging, and never accept it from request input. Base64 validation must use constant stack space and preserve the 15 MiB decoded limit.

**Tests use the real handler.** Build it with `makeApiHandler(makeTestAppLayer(world, options))` from `server/testing.ts` and send `Request`s; assert on the response and on the in-memory world (reviews, audit events, image files, cache invalidations). Do not `vi.mock` modules for API tests. See [docs/api.md](../api.md) for design decisions and compatibility.
